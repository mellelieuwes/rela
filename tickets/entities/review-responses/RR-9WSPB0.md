title: 'Design review: BaseVersion ''after write'' cannot be obtained correctly'
finding: 'Pull says ''BaseVersion := version after write'' (design:243), but there is nowhere to get that version. entity.UpdateResult has no version field (internal/entity/writeapi.go:74-77), and updateCore throws away the post-write version that UpdateEntityIf returns (`if _, err := m.deps.Store.UpdateEntityIf(...)`, manager.go:1174). That returned version is exactly the one storetest/cas.go:44-45 pins as the post-write token. The two workarounds both fail. (a) store.VersionOf(result.Entity) hashes each value''s %T, and fsstore reflows the body on write (store/version.go:113-141; fsstore/markdown.go:181), so the in-memory entity (float64 from JSON, unreflowed body) never matches the stored row. LocalChanged would then be true forever and every twin would stay pending. (b) Re-reading after the write races a concurrent writer: that user''s change gets stamped as the synced base, and its ours/shared edits are never pushed (a lost update). Related problem: when Plan.Patch is empty, PatchEntity still runs the full updateCore because there is no IsEmpty short-circuit (manager.go:1078-1081). Every in-sync pull would therefore write an update audit row and fire on-update automations. Fix: add `Version string` to entity.UpdateResult, fill it from UpdateEntityIf''s return value in updateCore, and use it as BaseVersion. When Plan.Patch.IsEmpty(), skip PatchEntity and use the version captured at the pre-reconcile read.'
severity: critical
resolution: 'entity.UpdateResult gains Version, filled from the token UpdateEntityIf returns (updateCore no longer discards it); Pull uses it as BaseVersion and skips PatchEntity entirely when the plan''s patch is empty. While verifying this, fsstore turned out to return VersionOf the caller''s entity instead of the normalized row it stored: fixed to return the version of what is on disk, pinned by storetest CAS/ReturnedVersionSurvivesNormalization. Tests: TestPatchEntity_ResultVersionIsTheStoredVersion; CLI sync-loop test shows an identical second pull writes nothing.'
status: addressed
